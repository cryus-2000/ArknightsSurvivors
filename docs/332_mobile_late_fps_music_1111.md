## 2. 终局配乐：哪两首、为什么同驻、怎么改

### 2.1 原因

不是两首曲子，是**同一首最终 Boss 曲的两层**：偏执泡影的配乐是 p1（一阶段底层）+ p2（二阶段加强层，叠在 p1 上）两条分轨（`suno_layers.json`，实测两轨相关 0.26、相加峰值 0.986，确实是叠加分轨，不是两版完整混音）。

docs/319 §22 已经把 p2 改成「听得见才解码」（`web/mobile_music_lazy_layer`），所以 10:00 登场时配乐只有 19 MiB；但 Boss 半血进二阶段（`set_final_phase(true)`）后 p2 要出声，浏览器解出第二份单声道缓冲，两份同驻到曲终：19 → 37 MiB。真机 11:21 正是二阶段后段。结算主题曲在 WIN 之后才 `play_settle`，不是它。

### 2.2 改法（以 docs/319 §12 / §15 / §22 的现有实现为起点）

- **出包**（`tools/web_music.py`）：另存一份 `music_suno_final_p12_mono.m4a` = 单声道 p1 + 单声道 p2 的预混（同采样率、同编码器，AAC 起始延迟与 p1 一致；码率 × 0.65 同战斗加层）。实际编码后与 p1 的最佳对齐延迟 0 样本；对原曲的残差 −10.1 dB，旧路径（p1_mono + p2 两次编码相加）−11.7 dB，同一量级。包体 +1.61 MB（只做结局一偏执泡影；另三首结局 Boss 各 +1.6 MB，Toy 50 MB 线放不下，列为后续）。
  顺带修：原来循环里处理完一首就删它的 OGG，处理 p2 时 p1 已经删了，预混读不到——改成全部处理完再删。
- **播放**（`tools/web/web_music.js`，只在手机单声道口径 `MONO` 下）：p2 的占位器解码的是预混。预混开播那一刻（`AudioBufferSourceNode.start(when)` 的同一个 `when`）用 `setValueAtTime` 把 p1 的增益切到 `g1 − g2`（二阶段两层都满 = 0），样本级交接、不叠也不空；再过 0.1 秒停掉 p1 并丢掉它的缓冲。
  - GDScript 一侧（`sfx.gd`）不动：它照旧以为两层都在播、照旧发两层的音量；JS 按「预混 = p1 + p2」把底层只补差值。整组淡出时两层同降，差值一直是 0，底层不会复活。
  - 二阶段退回（预混音量降下来）：重新解 p1，按预混的播放进度对齐接上；再进二阶段再放掉。
  - 预混文件缺失 / 网址 `?muspremix=0`：照旧解 p2 原文件（两份同驻，与旧版一样）。
- 战斗曲三段手机只放底层（docs/319 §3），Boss 曲单层，商人 / 标题等换曲已是「旧曲淡完立刻放」（`_free_after`），不涉及。

### 2.3 快检 `web_music`

`python tools/check.py --only web_music`（`--auto` 也跑，<1 秒，不开 Godot）。

交接里要求「仿照 `opening_transport_probe.gd` 用 weakref + `ResourceLoader.has_cached`」，但手机网页的配乐根本不是 Godot 资源：docs/319 §12 起长配乐出包成 AAC、由浏览器 `decodeAudioData` 解码，驻留的是 JS 里的 `AudioBuffer`，GDScript 侧只有一个 800 字节的静音占位流；weakref / `has_cached` 看不到它，桌面上所有分层播放器又是开局就建好、整局持有，探针在桌面上必然「两层都在」。所以锁的是真正驻留的那一层：

- `tools/web/web_music_selftest.js`：假 Web Audio（24 kHz、单声道留存，同手机），加载**仓库里真实的** `web_music.js`，按 `sfx.gd _wm_sync` 的调用顺序走：一阶段 → 二阶段（懒加载层听得见才 play）→ 交接 → 整组淡出 → 曲终 stop + free；另走二阶段退回、预混缺失、`muspremix=0`。判定读 `__syMus.mb()`（实际留着的解码缓冲）与源的开停 / 增益时间线，异步解码用真实的 Promise 轮转、定时器按假时钟推进（等价于「等音频线程回收」）。
- 拿 main 上的旧 `web_music.js` 跑同一个自测：8 项失败、二阶段 37.2 MiB；新版全过、18.6 MiB。
- 没有 node 的机器（GCP 镜像目前没装 node）记为跳过、不算失败。

## 3. 后半局帧率

### 3.1 量法

- **网页同局轮换**：`tools/perf_web.py run --mobile --dpr 2`（Edge 手机视口 844×390 × 2 ≈ 真机 1788×772 画布，触屏、24 kHz 音频，走手机网页的全部代码路径），
  `--balance --nodeath --bot=expert --realtime --perf --perfmin --rtfrom=<秒> --maxt=640 --seed=8724824136917219965 --op=exusiai --squad=mizuki,suzuran --norecruit --quality=mid --mobilecap`。
  `--mobilecap` 要带：不带时平衡模式下同屏上限 / 掉帧档的上限都不生效（`game.mobile_cap()`），和真机不一样（第一轮基线就是这样漏的，`PF SLOWMODE ... cap=0`）。
- 新旧写法用 `--wdab=30:48` 每 30 帧轮换（性能桶 `/wd0` 旧、`/wd1` 新），只读同一局同一分钟内两桶之差。
- 找大头用「整块拿掉」上限轮换（临时开关 `--tmpab=30`，分支 `tmp/late-fps-ab-1111` 11371692b / 687138bea，**不合入**），同样只看同局相对差。
- 分块计时探针（`--prof`）只用来**定位**，不用来估收益：开 `--prof` 时同一场景整帧从约 28 ms 变成约 60 ms，放大一倍多（与 docs/50 的经验一致）。
- 本机负载在几轮之间波动很大（同一场景基准 25–63 ms），所以只比同一轮内的桶，不跨轮比绝对值。模拟手机的绝对帧时比真机低约 1/3（真机 7 分钟后 P50 47 ms，模拟 28–33 ms），比例可参考、绝对值不可。

### 3.2 7 分钟后为什么变慢

1. **水月的成长节点提示环**。水月后期的节点（缠住 / 重斩 / 强迫性重复 / 群体性癔症，seg_mizuki.gd）每次命中都推一个贴地提示环（`fx_pxplane_cue`，同屏至多 32 个），
   每个环按美术像素逐格 `draw_rect`：半径 160 的环一圈约 500 个采样点 × 3 格 ≈ 1500 次 GDScript 调用。节点是随局逐步学会的，所以前 7 分钟几乎没有、后半局常驻十几个——这正对上真机「7 分钟后突然变慢、而且再没回来」。
   探针定位：水月贴地层里约 85% 是这一项。
2. **铃兰狐火光域**。每拍（15 次每秒）重算一遍光域像素表（`aura_ring`：逐点 cos / sin + Vector2i 字典去重），后期学会「暖光」后常驻 mode 1，点数更多。
3. 整块上限（同局轮换，模拟手机 7–10 分钟，基准约 27–61 ms，已含上面两项的新写法）：

| 整块拿掉 | 省（同局相对差） | 备注 |
|---|---|---|
| 干员贴地层（三人合计） | −1.6 ~ −4.7 ms（另一轮 −10~12 ms，基准 61 ms 时） | 铃兰 −2.2~3.0、水月 −1.8~2.3（其中提示环 −1.1~2.8）、能天使与 pfx 在噪声内 |
| 光学层（`--stackab` 32） | −7 ~ −9 ms（基准 61） | 含后期合成；GPU 侧，降它就是降画面 |
| 界面层（整层不画） | 约 −6 ms（基准 61），绘制调用 410 → 290 | 掉帧档已经隔帧画 |
| 全部敌人本体 | −3 ~ −8 ms | docs/319 §22.4：手机不拼图集，合批不成立 |
| 干员技能上层 | −1 ~ −3 ms | |

4. 8:06 / 9:41 的尖峰：同种子复现局在这两处没有对应的单帧尖峰（模拟里 P99 在 8 分钟段最高，但没有单帧 90 ms 级）；8:00 前后是第 2 只中期 Boss 战后普通刷怪回满 + 精英间隔缩到 32 秒（waves.json 第 6 档，520 秒起），9:41 附近是最终 Boss 9:30 预读（`PF PREFETCH t=570 e_paranoia`）之后。真机这两处更可能是贴图首次上传 / GC，**需要真机性能报告的逐秒帧与快照对照才能下结论**，本轮没有改。

### 3.3 改了什么（只改绘制，逐位一致，不改玩法 / 数值 / 画面）

| 项 | 做法 | 等价验证 | 退回 |
|---|---|---|---|
| 提示环合批 | `fx_pxplane_cue._ring`：合批画布开着时整环像素格写进一个三角形数组（`batch_canvas._quad` 的点序、`add_quads` 里同一 `_dim` 调色），一次接到批尾；发光点次序不变 | 144 组（6 个半径 × 断口 × 三种配色 × 画布变换 × 调色）顶点 / 颜色数组逐位相同 | `--wdold=16` / `--wdab=N:16` |
| 铃兰光域快速版 | `fx_pxplane_sz._aura_px`：mode 0 / 1 走预计算采样表（同一 R 建一次，内外圈共用去重编号，逐帧只做亮段判断 + PackedByteArray 去重）；mode 0 按旋转格取键 | 14 个半径（含来回切换）× 300 拍 × 2 模式 = 8400 组与 `aura_ring` 逐项相同 | `--wdold=32` / `--wdab=N:32` |

两项都只在绘制里，无头批跑不画世界层，TRACE 不受影响。

**结论：后半局每帧约省 1–1.4 ms（约 4%），P95 省 2–3 ms；按真机约为模拟 1.5 倍折算，真机后半局 P50 约 47 → 45 ms，到不了 34 ms 目标。**
剩下的大头在光学层、界面层与敌人本体（§3.2 表），GDScript 侧能逐位不变地抠的已经不多（docs/319 §22.5、docs/330 结论相同）；要到 30 帧需要 §3.6 里降画面的方案，等用户定。真机复测时看性能报告里 7 分钟后的 P50 / P95，与本次 47 / 58 对照。

### 3.5 掉帧档有没有用

- 真机：掉帧档 424 秒覆盖整个后半局，而 P50 仍是 47 ms——说明**它进得不晚，但降得不够**：它只做两件事（界面隔帧重画、同屏上限 65 → 50），合计约值 3–5 ms；后半局缺的是 13 ms。
- 进档条件（EMA > 40 ms 持续 3 秒）在真机 7 分钟左右就满足了，再提早没有意义；出档要 EMA < 34.5 持续 8 秒，真机后半局一直到不了，所以一直在档里，这本身是对的。
- 同屏峰值 66 > 50：上限只管普通刷怪排队，中期 Boss 召唤 / 精英 / 大群引导不受它管，峰值是这些叠出来的。

### 3.6 要降画面才能再省的（只列方案，没做，需用户定）

按模拟手机的上限轮换排序；都只在掉帧档里生效，正常帧率时画面不变：

1. **掉帧档里光学层降一档**（例如只关焦散 / 半分辨率发光，`optical.auto_mask` 现成的位）：上限 −7~9 ms（模拟，基准 61），是剩下最大的一块。代价：后半局水下光感变弱。
2. **掉帧档里提示环减量**：只画最新 N 个（例如 8 个）或只画进画面的；上限约 −1~3 ms。代价：水月后期命中提示变少。
3. **掉帧档里界面层再降到每 3 帧一画**：约 −1.5 ms。代价：血条 / 数字 10 次每秒更新。
4. 不建议：降渲染分辨率（docs/330 §6：CPU 受限，省不到）、再降同屏上限（是玩法改动，归数值会话）。
