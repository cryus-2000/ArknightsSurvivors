## 0. 死因分析结论（先看这个）

数据：云端结果分支 `cal1029-*` 全部 21 个（A–E、P1–P3、Q0–Q3、R1–R4、S1、S2、T1、T2，高手机器人 `expert`，难度 0、标准档，起始干员 7 种 × seed）共 2254 局，失败 1538 局。其中 **301 局是「超时未死」**（打到 780 秒上限，最终 Boss 没打完，生命还是满的），不是死亡，单列；真正死亡 **1237 局**，全部有最近 15 秒掉血明细。代码为 9432c412c 到 ba5c4d658 一带（relic-pacing 合入之后），T1 就是 aeef41137 的临时缺省；只看 R/S/T 九组（896 局，死亡 500）结论一致，下面写全量，括号里是 R/S/T。

1. **「暴毙」主要是普通怪围死，不是 Boss、不是精英单下**：死前 5 秒窗口按承伤额，普通怪 74% / 溟痕 6% / 敌弹 6% / 侵蚀创口 5% / 熄灯 5% / Boss 2%；按「主因」计，普通怪 84%（R/S/T 82%），其中 `contact_tracer` 一个来源就占 30%，其次 `contact_reaper` 12%、`atk_tracer` 11%。典型死法：死前 5 秒还有 ≥50% 血的占 50%，5 秒内挨 **4 下**（中位）、合计吃掉 **0.66 倍最大生命**（P90 0.99），其中最后 2 秒就掉 **0.28**（P90 0.60）；69% 的死亡局死前 15 秒场上敌人峰值 ≥60（大群）。分时段：0–4 分 96%、4–7 分 90%、7–10 分 76% 的主因是普通怪；7–10 分溟痕升到 17%，中期 Boss 在场期间主因仍是普通怪 64%（Boss 招式 15%）。**最终 Boss 段几乎没有死亡**（16 局，占死亡 1%），那里的失败是超时（301 局）。
2. **溟痕 / 熄灯是放大器，不是主因**：死亡时灯火「寂灭」占 37%、通明只占 18%（常规档 3/4 时间灯火 ≥70，所以败局里灯火明显更低）；15 秒内有熄灯掉血的 36%，但窗口里熄灯只占承伤 5–6%；死因最后一笔是 `wound`/`corrode` 的占 51%，但那是持续伤害的最后一滴，不是真凶。
3. **2 秒上限在起作用，但没有挡住暴毙**：失败局里 15 秒内最大的 2 秒滑窗达到或超过 `any_2s_cap 0.70` 的占 **15%**，贴近（0.63–0.70）再占 **16%**，合计约 1/3 的败局贴着上限；死前最后 2 秒窗口本身 ≥0.70 的只有 5%（中位 0.28）。说明上限只截住了极端的那几秒；普通死法是 4–5 秒里每下 15–25% 最大生命的接触伤害连续落下（单下最大中位 0.21，≥0.25 的败局占 26%，≥0.40 只有 2%）。

**哪些只是粗估**（字段不足，见 §1.4）：「大群」只有 15 秒内敌人数峰值，没有逐下的在场数；「精英」只能按类型（role=elite）识别，不认个体精英化标记；Boss 子弹和普通敌弹同记为 `bullet`，只能靠「Boss 在场」推断；2 秒上限 / 单下上限**游戏里没有触发计数**，上面是用明细反推；熄灯的持续掉血（每秒 3 点）不在逐笔明细里，按 `last15.dark_s × 3` 折算；逐笔明细按 tick（0.066 秒）合并同来源，所以「挨了几下」和「单下」是 tick 口径，偏大（同一 tick 多只怪接触会合成一笔）。

复现：
```
python tools/death_report.py <含 BALANCE json 的目录或文件>... [--bots expert,master] [--cap 0.70] [--swarm 60] [--sudden 0.5] [--out build/death_report.md]
```
（云端结果分支的 json 在 `build/cloud/<tag>/*.json`，用 `git show origin/cloud-results/<名>:<路径>` 取出，或开临时 `git worktree add --detach`。）

### 2.4 死亡前时间线（死因分析的核心缺口）

现状是 15 秒环形缓冲（`ring` 掉血明细 + `ring_ctx` 只存峰值）。提案：把 `ring_ctx` 从「峰值」改成**每 0.5 秒一格**的快照，和掉血明细对齐：

`death_tl` = 最近 15 秒的 `[t, 主控 hp, 灯火, 在场敌人数, 离主控 150 / 300 以内的敌人数, 敌弹数, 护盾 / 减伤状态位, 站位(是否被围: 8 向被堵数), 主控移动速度, 冲刺 cd 是否可用, 队友存活数]`，30 格 ≈ 1.5 KB；掉血明细每笔补 `ty`（来源敌人类型）、`elite`（0/1）、`pre`（上限 / 护盾截之前的量）、`cap`（被 2 秒上限 / 单下上限截掉的量）。这样一次性回答：围了几只、有没有退路、冲刺能不能用、上限挡了多少。体积 ≈ 4 KB / 局（在现有 5.5 KB 的 `end` 上换格式，净增约 +1 KB）。

**同时记「险境未死」**：每次生命掉到 <20% 但活下来时，存一份同样的快照（每局最多 3 份，共 ≈ 3×1.5 KB），用来对比死亡局与险境局——不然只能看到「死的那些」，无法说明哪些特征真的致命。

## 3. 其他共通指标：玩家输入强度

## 4. 体积、性能与隐私总则

- **体积**：整局记录现均 26 KB（上限 69 KB）。提案新增总计目标 ≤ **+12 KB / 局**（均值），单局硬上限 **≤ 100 KB**（含现有）；`runs.jsonl` 仍是约 8 MB 丢较早一半，约 300 局。
- **性能**：全部是事件处 append 或 ≥10 秒的定频累计；每帧新增开销要求 < 0.05 ms（当前帧预算按手机网页 30 帧、入门本 60 帧，docs/50）。逐 tick 的工作（`ring`、`ring_ctx`、掉血明细）本来就只在 `g.bot != null or Mode.PLAY` 分支里跑；**提案不扩大这个范围**：`death_tl` 的 0.5 秒快照只在记录开着（`runs_log_enabled()` 或 `--balance`）时采，对外包和网页公开版零开销，不改变现状。
- **开关分级**：
  - 常开（调试 / 对内 / 批跑）：事件型与 ≥10 秒定频；
  - 仅 `--balance --telemetry=full`：逐 tick 级（`pre/cap` 截前量、近身敌人数），云端批跑用，批跑也不画世界层所以开销可接受；
  - 对外包：恒关（沿用 `Cfg.runs_log_enabled()`，不新增例外）。
- **隐私**（docs/40）：只写本地文件；不联网；不记账号、设备号、IP、玩家名、系统用户名；`input_kind` 只有三个枚举值；不记逐键 / 逐帧输入序列；`time` 保持 UTC。新增字段落地前要过 `check_release.py` 第 6 项（`save_local` 只经 `Cfg.runs_log_enabled()`）。上报通道仍按 docs/43 暂缓。
- **兼容**：只加字段不改 `SCHEMA`；`balance_run.py` / `runs_report.py` 读不到新字段时用缺省值，旧 json（含现有云端结果分支）照常能读。
