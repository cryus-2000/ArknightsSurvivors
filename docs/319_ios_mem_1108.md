# 319 · iPhone 真机开局内存 600 MB：拆账与修法（11-08，帧率会话，分支 claude/ios-mem-1108）

> 协调人转用户 11-08：Toy 预览 ed28cd083，iPhone（iOS 26.6.2，Safari / B站 App，中画质自动、锁 30）三份性能报告——
> 首次进游戏那局 0:39 峰值 600 MB（贴图 442 / 音频 137 / 缓冲 21），之后两局 500–502 MB（贴图 343–344 / 音频 135–137），并出现过真实的内存崩溃（页面崩后自动刷新）。
> 硬门槛：**开局 < 400 MB**，Toy 首发前必须压下来。编队：维什戴尔（队长）+ 安洁莉娜。

## 0. 结论

1. **Edge 手机仿真以前严重低估，是因为测量走 `--balance`，跳过了标题页**。只要走玩家路径（标题 → 图鉴 → 出发 → 载入页 → 进局），仿真就和真机对上：开过图鉴 579 MB（真机 600）、没开 511 MB（真机 500）。
2. 大头三块（都是「手机没有例外」的预读，不是贴图格式问题——帧条本来就是无损导入、显存里一律 RGBA8，桌面 / iOS 同一口径）：
   - **图鉴 `gallery._warm_demo`**：一打开图鉴就把整局名单（全员 V6 特效 + 全部敌人 + 白剪影）读进静态贴图缓存，约 **+256 MB**，关了图鉴、进了局都不放。首次进游戏的新手引导会强制开图鉴，所以第一局多约 100 MB。
   - **载入页 `loading_warm_lists`**：预读名单 `preload_tex_names` 含**全员**的 V6 特效帧条（约 150 MB），进局后手机按需读特效（`lazy_fx`）其实只用队长的，剩下的整局留在缓存里。
   - **战斗一配乐三层整首全解码**（599 秒 × 24 kHz × 双声道 × 4 字节 ≈ 110 MB）。10-26 定的「手机只放底层」（b53b835bf）在 6b3275b74 删旧乐句拼接时一起丢了。
3. 修完（仿真，进局 t=0，显存 + 音频）：**开过图鉴 579 → 264 MB，没开 511 → 260 MB**，都在 400 线下；维什戴尔 + 安洁莉娜打到 2:00 是 220 + 39 = **259 MB**（贴图随新怪 / 新特效涨到 165），后期留出约 130 MB 余量。真机数字要用户在新包上再报一份确认。

## 1. 量法

`tools/perf_web.py run --mobile --dpr 3`（Edge，iPhone 横屏 844×390 @3 仿真）+ `--memlog --ftrec --quality=mid --op=wisadel`，**不带 `--balance`**，用标题页的 `--ftdo` 脚本动作走玩家路径：

- 开图鉴：`--ftdo=title:3:gallery --ftdo=gallery:4:gal_next --ftdo=gal_next:3:gal_tab --ftdo=gal_tab:3:close --ftdo=close:2:go`
- 不开：`--ftdo=title:3:go`（`go` 是这次加的测量动作：同难度页「出发」，预热 → 载入页 → 进局）
- 旧口径对照：`--bal=web/mobile_drop_outrun=0 --bal=web/mobile_music_lite=0 --bal=web/mobile_gallery_trim=0`（同一个包）

音频按引擎补丁 `window.__syAudioMB` 读 Web Audio 缓冲的实际字节（网页无线程版按「样本」播放，不论源文件是 OGG / MP3 / WAV，播放前整段解码成 Float32 PCM 驻留，占用 = 时长 × 上下文采样率 24 kHz × 声道 × 4 字节；**转 MP3 不省内存**）。

## 4. 第三份报告 2:06–2:08 的卡顿（10–14 帧，单帧 95–177 ms，无「读贴图」）

- 最可能是**护栏第 1 步「清缓存」**：`game._mem_guard_apply` 超 520 MB 时 `Cfg.slim_fonts(true)` 清掉全部字形缓存，下一帧起屏幕上每个中文字号都要重新光栅化（HUD、飘字、升级卡），真机上就是连续几帧百毫秒级；同时立刻释放不在场的白剪影 / 敌人帧条，之后再刷出来又要现读。报告里「护栏已触发（只清缓存）」与时间吻合；单秒标签只记「读贴图」（`A._cache` 张数增加），清字形不在自动标签里。
- 口径：护栏读数 = 引擎显存统计 + `__syAudioMB`，每 5 秒一次，阈值 `MG_BUDGET_MB` 520；性能报告的峰值另按 `MEM_EVERY` 采样，所以报告峰值 500 而护栏触发是可能的（两次采样之间短暂过线，例如换曲时两首同驻或载入大图）。
- 处理：治本是本文的修法——开局 260 左右，后期不再碰 520 线，护栏不会在局中触发。若还要加固：清字形改成只清当前没用到的字号，或延到升级 / 暂停等界面暂停时再做（另立项）。

## 7. 连开两局（11-08 下午，用户 iPhone：第一局 5 分钟死 → 回标题 → 开第二局时页面被强制刷新）

### 7.1 量法

测试参数 `--tworuns`（`run/autotest.gd`）：平衡局第一局到 `--maxt` 按倒下进结算，停 4 秒 → 回标题 → 标题页照 `--balance` 自动再进一局；第二局正常收尾。网页仿真 `--mobile --dpr 3`，`--realtime --rtfrom=240 --maxt=300 --seed=13 --op=wisadel --squad=angelina --quality=mid --memlog --ftrec`。`--memlog` 加了 `PF MEMJS`（WASM 线性内存容量 + JS 堆，引擎显存统计看不到的那部分）。

合入 Codex `codex/mobile-frame-architecture-1107` ada52f31e 后（高清干员画布 op_node 离场释放、按编队预热），又发现 Codex 的失焦自动暂停（docs/317）会让屏幕外的测量 Edge 卡在开局：机器人测量局（`--balance`）不再自动暂停（c46a6474b）。

### 7.3 改法（`game._release_run`，手机网页，`--bal=web/mobile_run_release=0` 退回；桌面 `--runrelease` 试）

- 贴图：第一次进标题时记启动期缓存键（`A.mark_boot`），离开一局（回标题 / 重开，`_exit_tree`）把之后进缓存的全部拿掉（`A.drop_run`）；直接重开不过载入页，保留同编队的固定名单。下一局在载入页按新编队重读（载入多几秒）。
- 音频：局中 `Sfx.ensure` 补进来的音效（终结技等）从音效表拿掉，连同历史语音一起 `__syAudioFree` 退样本（语音按双声道注册，237 条全播过约 99 MB）；还在播的跳过。
- 桌面无头跑 `--tworuns` 退出时会段错误（两版都有，开窗口正常退出），只影响桌面无头测试收尾。

## 8. 局中整屏发紫 / 粉

和 toy-shell 会话（docs/318、claude/toy-shell-bdac50）对过：外壳页面里没有粉色，像素反推是**页面外的原生层**（约 19% 罩 + 2 像素亮边 + 顶部灰进度条），即 B站 App 容器自己盖的，游戏画不到那一层。它和崩溃重载后的粉色是同一个东西，最可能是容器在网页无响应 / 内存告警时盖的「加载 / 恢复中」层，所以可以当作「快崩」信号。和内存峰值的时间关系仿真里看不到，要真机对：请用户下次看到粉罩时记下对局时间，和性能报告的最慢 5 秒 / 护栏触发时间比；新包内存降下来后它应该不再出现。

## 9. 局中白屏（11-08 晚，main 3500acd18 真机：两局分别在 3 分多、7 分多钟白屏后被强制刷新）

能留下报告的只有 0:51 退出那一局：显存 + 音频峰值 269 MB（贴图 180 / 音频 67 / 缓冲 21），护栏（520 MB）没触发。崩掉的两局不到护栏线，所以要看的是**引擎统计看不到的部分**和**尖峰**。

### 9.1 崩溃前快照（`core/crash_box.gd`、`core/crash_note.gd`）

- 真玩家局（无命令行参数；测试加 `--crashbox`，`--crashbox_every=<秒>` 改间隔）每 15 秒同步写一条进 `localStorage['sy_bb']`：局内时间、贴图 / 缓冲 / 显存 / 音频样本 / **WASM 容量 / JS 堆** / 节点数 / 对象数 / 同屏怪 / 特效 / 弹 / 等级 / 贴图缓存张数 / 这一段新读贴图张数与最后 6 张名字 / 这一段的事件标签（Boss 登场、读帧条、护栏…）。显存 + 音频比上次写入涨 24 MB 以上立刻多写一条（标签「尖峰」，最快 3 秒一次）。
- JS 侧直接往同一份记录追加页面事件：WebGL 上下文丢失 / 恢复、切后台 / 回前台、页面隐藏、脚本错误、未处理的 Promise 拒绝（主循环卡死也写得进）。
- 局终 / 回标题 / 重开记 end。下次启动没有 end = 异常退出，挪到 `sy_bb_prev`：标题页左下角一行「上次对局异常退出（局内 m:ss，显存 + 音频峰值 N MB）· 点此查看 / 复制」，点开是可复制 / 保存的曲线文本；设置 → 画面 → 性能报告的「复制报告」也附上这份（即使没有局终报告）。
- 桌面无头验证：跑到 23 秒杀进程 → 再启动，`PF CRASHBOX prev=1`，曲线 8 行、最后新读贴图名单都在。

- 机器人局几乎不出语音（音频只涨到 45 MB）；真玩家局每句说过的语音都按双声道 float 留到离局（0:51 那局音频已经 67 MB）。

### 9.3 改法

- **局内语音预算**（`sfx._voice_trim`，手机网页）：每读一句新语音前，已注册语音超过 10 MB 就按最久没播先退（正在播的不动，下次再说时重新解码约 10–30 ms）。`--bal=web/mobile_voice_trim=0` 退回。
- **切回 App 没声音**（`tools/web/power.js`）：回前台后的前 2 下手势里，每个音频上下文在手势内同步 suspend 再 resume（重新接上输出）、重放 1 帧静音缓冲，再播一段静音 `<audio>`（让 WebKit 重新激活媒体音频会话）。以前一看到 state 已是 running 就撤掉手势监听，iOS 26 上回前台时非手势 resume 会把 state 置回 running，但输出没接上。另加 1 秒看门狗：页面可见时状态不是 running，或 running 但 `currentTime` 不走，就重新挂手势监听。窗口 focus 只补 resume、不重启。自测 `node tools/web/power_selftest.js` 21 项通过。真机待测。
- `--memlog` 每行加贴图缓存去重合计和新进缓存的贴图清单（按大小）。

### 9.4 没做 / 待真机快照定

### 12.1 改法

- **导出**（`tools/web_music.py`，`export_web.py` 与测量副本 `perf_web.py` 共用）：≥ 30 秒的配乐（24 首：标题 / 图鉴 / 选人 / 商人 / 全部 Suno 分层与 Boss 曲）不进 `index.pck`，转成单独的 AAC `music_<名>.m4a`（平铺在根目录，Toy zip 只收根目录），码率 = 原 OGG 平均码率 × 1.15 + 2 kbps；副本里写 `audio/music/web_music.json`（曲长 / 网址）。开场引子、Boss 登场 / 击破短句仍在主包走引擎样本。为什么是 AAC：iOS 的 `decodeAudioData` 不保证认 Ogg Vorbis。

### 15.1 量法：堆里实际在用多少

### 21.2 快照 0:41 后停写（根因）

`CrashBox.on` 是静态变量。局中精英化演出（elite_show）和图鉴演示建的演示用对局实例，在 `_ready` 里也调 `CrashBox.begin`，算出「这是演示，不记」后把 on 写成了 false，正在记的本局快照跟着被关掉。之后每次采样、阵亡时的 end 都直接返回，所以停在 0:41（那一刻正好精英化）、局终没有 end，被判成异常退出。仿真里机器人局没有精英化演出，所以复现不了。

改法：演示实例在 begin 里直接返回、不碰共享状态；快照记下是哪个对局实例在写，tick 只认这一个；演示局倒下也不写 end。另外加了两样诊断，写进快照文本：写入失败的原因（sy_bb_err：报错、时间、数据长度、本地存储已用量）和心跳（sy_bb_hb：实时秒 / 局内秒），下次再有问题能看出断在哪一步。

## 23. 最终阶段内存账与再往下压的路（11-09，目标最终 Boss 阶段总计 ≤ 650 MB）

### 23.1 量法

`--texwalk`（frame_rec）每个快照点打两行：
- PF TEXFILES：用 `ResourceLoader.list_directory` 走 res://art 等目录，`has_cached` / `get_cached_ref` 找出所有从文件读进来、现在还活着的图，不管谁拿着，按目录归类。

引擎没有把逐张贴图的显存表开放给脚本（RenderingServer 只有总量），所以两者都找不到的那部分只能靠对照推断。

## 22. 世界绘制优化结果（11-09，分支 claude/eager-ride-4bv38c，基于 main d55e5d450）

任务：不改画面，降世界绘制每帧 CPU（协调人转来的 §21 仿真拆账：世界绘制 20–22 ms，其中排序实体 6、敌弹 3、溟痕 3、护盾无人机 2.3、场地 2、影子 1.7）。

### 22.1 量法

- **性能**：同局轮换净差。`--wdab=30[:掩码]` 每 30 帧把新写法整项换回旧写法，性能报告分 `/wd0`（旧）、`/wd1`（新）两桶；`--fixed-fps 60 --balance --perf --prof --realtime --rtfrom=<秒>`，能天使单人 `--norecruit --seed=13 --quality=mid`。只读各桶的「世界绘制 / 敌方顶层 / 发光层」整段计时之差，不靠分块探针估。
  云端 Linux 两种环境：Xvfb + opengl3（软件 GL，带光学发光层；帧时被 GPU 模拟拖到 120–130 ms，只看 CPU 段差）和无头 `--drawtest`（只有 GDScript 绘制，没有发光层）。`--noatlas`（新，仅测试）让桌面也不拼敌人图集，走手机网页的原帧条路径。都是原生 GDScript，手机网页（WASM）上绝对值约大 2–3 倍，比例相近。
- **画面**：同 seed 固定帧截图（1:38 / 2:30 / 3:45 / 4:00 / 4:59，覆盖溟痕、黑潮圈边、普通怪 / 精英、塑路者第二版弹幕），干净局（不用接管式探针）。
  按墙钟走的画面元素会让同 seed 两次截图本身就不同（光学后处理水下焦散的 `time`、地面荧光斑明灭、GPU 粒子、颗粒令牌桶按真实时间补充）：旧对旧第一次比对就有 5 千–14 万个像素差。对照时两边都关掉这几项：
  `--stackab=0:3 --bal=render/optical_caustics=0 --bal=render/optical_ground_glow=0 --nohud`，之后**旧对旧 0 像素差**，再比新旧。

### 22.3 结果

| 项 | 做法 | 净省（原生，ms / 帧） | 画面对照 |
|---|---|---|---|
| ① 敌弹 | Boss 弹第二版粒子推进 / 绘制按种类序号查表，不再每粒建临时数组、查字符串字典；方块直接进 world 三角形批（顶点、次序、闪烁抽样次序不变）。`--wdold=1` 退回 | GL −0.12、无头 −0.14（敌方顶层段，3:35–4:35 塑路者弹幕在场）；没有 Boss 弹幕时 0 | 5 张 × 图集 / 无图集两条路径，逐像素相同 |

合计：后期常态每帧约 −1.0 ms，Boss 弹幕段约 −1.1 ms（原生）；按 WASM 2–3 倍折算，手机网页约 −2~3 ms，约占世界绘制的 10%。**单靠这三项到不了后期稳 30 帧**（真机 P50 44 ms，还差约 11 ms）。

回归：`tools/check.py` core / smoke（23 项）/ render_perf / render_lifetime / elite_mark_v2_review（--dccheck，dc_bad = 0）/ repro 全过。

### 22.4 试过但没留、或判断不该做的

- **敌人 / 影子改 MultiMesh 合批**：手机网页不拼图集（§16 / docs/50 §30，按内存优先），每只敌人的描边、本体、白剪影是三张不同贴图，按纵深穿插画，同贴图连续不起来，合批不成立；只有影子是同一张贴图，引擎已经自动合批，GDScript 侧只有 0.1 ms。MultiMesh 每个实例仍要在 GDScript 里逐只写变换 / 颜色 / UV，和现在逐只发一次绘制同量级，省不出来。
- **敌人缓存路径内联**（无图集时把描边 / 本体 / 白闪的调用链展开、受击反应与描边签名改每帧算一次、描边贴图按名字直取）：新旧逐像素相同、--dccheck 通过，但同局轮换量下来 +0.03 ms（噪声内），撤掉不留。
- **② 排序**：建键表 + 原生排序整段只有 0.25 ms，「排序实体 6 ms」几乎全是逐只绘制。改成「键两两不同时整表登记后原生排序」量下来也是 0，撤掉。交给引擎 y-sort 要每只实体一个 CanvasItem，引擎侧开销更大，不做。
- **护盾 / 无人机画进缓存**：两者本身几乎不花时间，这一段的耗时在干员技能上层与终结技指示，逐帧都在动，不适合缓存。

### 22.5 剩下的大头（原生，按收益）

1. 敌人逐只绘制约 1.2 ms（手机约 3–4 ms）：GDScript 每只 20 µs 主要是字典读写，要再降得换数据结构（例如敌人画面状态集中成定长数组）或挪到原生扩展，属于较大改动。
2. 干员立起层特效 0.65 + 技能上层 0.5 + 终结技指示 0.2–0.7：干员侧，按干员分开看。
3. 手机网页每只敌人三张贴图各一次绘制调用（不合批），引擎侧的提交 / 状态切换在真机上的占比要看真机报告；若内存余量允许，可考虑「拼图集后释放原帧条」，对显存是净零。
