# 50 · 性能测量（测试与验收，2026-09-30）

用户问「后期卡不卡」。本文记录测法、结果和待办；测量工具都在 `game/scripts/run/autotest.gd`，只在 `--balance` 下生效，不改玩法。

## 1. 工具

| 开关 | 作用 |
|---|---|
| `--perf` | 按游戏时间分段（0–8 / 8–10 / 10+ 分钟）记：真实帧时间、渲染 CPU / GPU 时间（RenderingServer 视口计时）、同屏敌人数。结束时打印一行 `PERF {...}` |
| `--prof` | 模拟步分段计时（enemies / bullets / spawn / squad / visuals …）；另把世界绘制 `draw_world` 单独计（它也算在下一帧的 `engine` 里）。配合 `--perf` 给出各段逐帧平均、慢帧（≥33 毫秒）分段，以及最慢 25 帧的场面（敌人 / 击杀 / 弹幕 / 预警 / Boss 类型） |
| `--realtime` | 按真实帧间隔推进，不多跑模拟步。**不加时**，`--balance` 每渲染一帧跑 8 步、每步 0.066 秒（≈ 真实游戏的 30 倍模拟量），帧时间不代表玩家体验，只能比相对差异（例如特效开 / 关） |

测法（必须开窗口，不能 `--headless`；本机其他 Godot 会把慢帧放大，正式测要协调「安静时段」）：

```
godot --audio-driver Dummy --path game -- --balance --perf --prof --realtime --seed=1 --op=mizuki --bot=expert --tier=0 --maxt=660
```

特效开关用临时 APPDATA 里的 `settings.cfg`（`[video] bloom / dof / normal_maps / water_filter`）；窗口 1920×1080 用 `res_index=1`、`fullscreen=false`。

## 5. 经验宝石：为什么会堆到 350 颗，以及「宝石上限 + 合并」三版实验（玩法系统，2026-09-30）

**为什么堆**：拾取范围只有 70（灯火 ≥ 70 时 ×1.2，< 30 时 ×0.7）；远程干员在 300–600 外击杀，宝石掉在那里；宝石没有寿命；磁铁稀少（小怪约 0.25%，精英 / Boss 必掉磁铁或回复二选一）。绕圈风筝的玩法下远处击杀点的宝石只进不出——真人也一样，不只是机器人不回头扫。

**隐性规则（run/pickups.gd drop）**：场上 > 350 颗时，新掉的经验**直接入账**、不生成宝石。机器人漏捡多，场上很早就过 350，此后大半经验靠这条「溢出自动拾取」获得。§3 看到的「350–360 颗」正是这条规则的上限。

**三版合并实验**（分支 gameplay/gemcap，未合入）：场上经验宝石 ≥ 150 时——
| 版本 | 做法 | 同 seed 对比（6 局普通 / 高手，基准 = main） |
|---|---|---|
| ① | 新掉的并进离掉落点最近的那颗 | 最终等级 ±2，中期到 Lv15 晚 1–2 分钟 |
| ② | 新掉的并进离主控最近的那颗 | 有的局 Lv10 从 207 秒拖到 408 秒 |
| ③ | 最远的一颗并进它的邻居，新掉的照常生成 | 最终 −1～−3 级；有一局 499 秒前几乎不升级、然后一口气跳约 10 级 |

三版的共同问题不是合并方式，而是宝石数被压在 150 以内后，350 的溢出自动拾取不再触发，经验被压在远处，只能等磁铁回收。

**决定（协调人 9/30）**：玩法不动（方案 C）。性能由绘制侧解决——界面与美术 0566e4f「> 120 颗时远处结晶合并画 + 屏外不画」。把溢出门槛从 350 提前到 150（方案 A：超了直接入账）会让中后期经验变快，等 close6b 收口后由数值评估是否进 close7。gameplay/gemcap 分支保留。

## 7. 音频：同时发声、峰值与开销（音频，2026-09-30）

测法：`--headless --audio-driver Dummy`，`--balance --realtime --seed=1 --op=mizuki --bot=expert --tier=0 --maxt=660`（标准、水月、高手），
测量脚本在 SFX / Music / Voice 三条总线上挂录音（Master 在自动化运行时静音，不动它），录音前先衰减 12 dB 免得 16 位录音截掉超过满幅的部分，
分析时补回并按各总线音量相加 = Master 输入（限幅器之前）。每帧数一次性音效 32 个播放器里有几个在响；`Sfx.sfx_stat` 记播放 / 合并 / 丢弃 / 抢占 / 降音量次数和 `play()` 耗时。
实时模式下同一种子也不完全复现，三局长度 422–684 秒。

| | 结果 |
|---|---|
| 同时发声（一次性音效） | 最多 22–23 个，99% 的帧 ≤ 15 个；从没碰到 32 个的上限 |
| 同名音 50 毫秒内合并 | 一局约 1.2 万次播放、1 万次被合并（同名音高频重复很普遍） |
| 峰值（限幅器前） | **+6.6 dBFS**（瞬间尖峰）；400 毫秒最响 −2.8、中位 −16.4 dBFS。尖峰主要来自单个很响的音效，不是数量堆出来的 |
| `play()` 主线程开销 | 每次 0.23–0.34 毫秒（大部分是引擎起播本身），一局平均每秒 4–6 毫秒，60 帧下每帧不到 0.1 毫秒 |
| 音频线程 | 混音在独立线程（网页是 Web Audio 自己的线程），Dummy 驱动下量不到混音耗时；测试与验收拆主循环也没发现音频拖慢帧率 |

处理（sfx.gd / settings.gd）：

- **优先级**：5 Boss 大招 / 阶段 / Boss 事件 > 4 主控状态与操作反馈 > 3 灯标、技能发动 > 2 一般攻击与敌人（缺省）> 1 拾取、击杀、命中。
  32 个播放器都在响时抢占正在播的最低优先级音，自己优先级不高于它就丢弃；已有 12 个在响时，优先级 ≤2 的音降 6 dB（激烈的一局触发约 1000 次）。
- **同名音 50 毫秒内合并**（各音原有的最短间隔更长的照旧）。
- **低画质档**（设置「画质：低」）：同时发声上限按 16 算，已有 12 个在响时优先级 ≤2 的音直接丢弃（高画质是降 6 dB）。引擎里 30 个普通音 + 1 个 Boss 大招同时触发：高画质 31 个在响、18 个降音量；低画质 13 个在响、18 个丢弃，Boss 大招照样出声。
- **网页版 Master 让出 7 dB**：网页是样本播放，总线效果不起作用，Master 的限幅器在网页上没用，+6.6 dBFS 的尖峰会直接削波。
  网页版整体比桌面版轻 7 dB，峰值落在约 −0.4 dBFS。桌面版有限幅器，不降。

## 8. 绘制调用次数（界面与美术，2026-09-30）

## 9. 敌人图集 / y 排序：测量与方案（界面与美术，2026-10-01，EA 后；待协调人定再动代码）

目标：8–10 分钟帧时间中位 18.8 → ≤ 14 毫秒（§8.1 高画质）。

### 9.1 现状拆分

### 9.2 方案 A：敌人帧条合成图集

- **做法**：开局加载时按 game.gd 的 e_* 加载表（有 @2x 用 @2x）把敌人帧条、白色剪影（受击白闪）、描边剪影（_outline_tex）一起打进一张图集，留 2 像素边防渗色；另存一份**水平镜像**的帧（像素图翻转现在靠 draw_set_transform(-1, 1)，换成取镜像帧就不用改变换）。各贴图记录图集内的区域，vfx.spr / _spr_outline 改成按区域取帧。法线光照开着时，用同样的排布生成法线图集，组成一个 CanvasTexture。
- **容量**：敌人帧条共约 2.4 M 像素（1× 79 张、@2x 20 张，最宽 1344），加白色剪影、描边和镜像帧约 10–14 M 像素，**一张 4096² 能放下**（16.7 M）。
- **收益估计**：排序段的 250 次贴图切换降到「被干员 / 道具打断」的约 20 次，敌人相关绘制调用约 390 → 约 120（影子、词缀特效、弱点菱形另算）。按 §8.1 每次调用的渲染线程开销（约 2.8 微秒）和 GPU 状态切换估算，**省约 1–2 毫秒**。GDScript 侧不省。
- **风险**：① 法线图集边缘渗色 / 光照接缝（靠留边 + 法线先在原帧上生成再打包来避免）；② 图鉴、精英化演出、Boss 演出等直接读 g.tex[e_*] 的地方要一起改成取区域，漏改会画错帧（需要全仓库 grep g.tex 的 e_ 用法）；③ 运行时打包增加开局加载约 0.1–0.3 秒（或者改离线工具生成 + 校验，避免过期）；④ 网页版贴图尺寸上限（4096 在 WebGL2 下可用，8192 不保证）。
- **工作量**：中（art.gd 打包 + vfx / world 取帧 + 图鉴等读点改造 + 截图逐像素对照），约 1–1.5 天。

### 9.3 方案 B：y 排序改桶排序 / 按行分层

- **桶排序**：sort_custom 在 172 条上只占约 5%（安静时段约 0.1 毫秒），改成按 y 分桶最多省约 0.1 毫秒。**不建议做**。
- **按行分层**（按 y 分几层、层内不排序）：会出现前后遮挡错误（同一行里后画的盖住先画的），而且不减少贴图切换。只有配合图集才有意义，单独做没收益。**不建议做**。

### 9.4 达到 ≤ 14 毫秒还缺什么

图集约 1–2 毫秒，离目标还差约 3 毫秒。按 profile，值得一起看的有：
1. **敌人本体绘制的 GDScript 开销**（排序段 2.5 毫秒的大头）：draw_enemy 每只都要查贴图、算帧、算镜像、算锚点、判描边 / 白闪 / 词缀。可以缓存每种敌人的贴图和帧参数，满屏时普通怪不画描边（现在只是变淡），直接用 RenderingServer.canvas_item_add_texture_rect_region 少一层包装。估计约 1 毫秒。
2. **HUD 2.2 毫秒**：编队栏、藏品栏每帧重新排版文字，可以缓存成「内容变了才重画」的子画布（HUD 拆成静态层 + 动态层）。估计约 1 毫秒。
3. **护盾 / 无人机 1.1 毫秒**：每架无人机每帧 4 次 draw_circle 外加 2 次变换，可以合批。估计约 0.5 毫秒。
4. **敌人模拟 2.9 毫秒**：玩法 / Boss与怪物那边的事（空间网格、AI 分帧），我这边不动。

**建议顺序**：先做 9.4-1 和 9.4-3（低风险、纯画面代码、约半天），再做方案 A 图集（中风险），最后视结果决定 HUD 分层。每步都在安静时段用 §8.1 同参数复测，测完写回本节。

### 9.6 要到 ≤ 14 毫秒：敌人改保留模式绘制（方案 C，待定）

- **做法**：敌人帧条打成图集（§9.2）后，用一个 MultiMesh（2D，带 instance color + custom data 取帧区域）画全部敌人：每帧按 y 排好序填实例（变换 = 位置 / 缩放 / 镜像，custom data = 图集区域，color = 染色 / 白闪），**一次绘制调用画完全部敌人**；描边、白闪各一层同样处理。GDScript 每只只剩写变换和两个向量（估计 1–2 微秒 / 只）。
- **收益估计**：排序段 GDScript 约 3 → 0.5 毫秒，渲染线程和 GPU 再省约 1 毫秒，合计约 3 毫秒，加上 ② 和 HUD 分层有望到 14 毫秒上下。
- **难点 / 风险**：① 前后遮挡：MultiMesh 按实例顺序画，敌人之间按 y 填序没问题；但和干员、博士、骑士、立体道具（约 10 个）交错的前后关系要么把它们也放进同一套绘制，要么接受「敌人整层在下、干员整层在上」（人群里干员会永远压在敌人上面）。② 每只敌人现在的特殊画法（狂暴红光、阶段护盾环、部件心跳、潜地波纹、词缀特效、Boss 专用帧条）要分流：普通怪走 MultiMesh，特殊状态 / Boss / 精英仍走原来的逐只绘制。③ 法线光照要配法线图集，用 CanvasTexture 给 MultiMesh。④ 着色器取帧要写一个小 shader。
- **工作量**：大（约 3–4 天，含逐像素对照）。建议先做图集（§9.2，本身就是 C 的前置），落地后用 --fixed-fps 60 量清楚，再决定上不上 C。

### 9.9 敌人画法缓存：方案页（架构，2026-10-01，待协调人定再动代码）

**先说结论**：§9.8 已经量过「只缓存定义 / 贴图名 / 贴图存在性」，收益在噪声内。说明那 89% 的选帧 / 状态逻辑不是集中在几次查表上，而是分散在整段 draw_enemy 里。这次缓存要省到可测的量，就得把「选帧 + 算颜色 / 尺寸」整段跳过，而不只是缓存查表结果。能不能省出来，取决于「判断缓存还有效」比「重新算一遍」便宜多少。所以**分两步：先量（第 0 步），可缓存部分 ≥ 1 毫秒再做（第 1 步）**，不够就像 §9.8 一样记下结论，不做。

**draw_enemy 现在每只每帧做的事**（render/world.gd 1080–1304 行）：
1. **选帧条与帧号**（约 70 行）：约 25 次 `e.get`、3–4 次 `D.ENEMIES.get(e.type)`、约 6 次「拼接名字 + `g.tex.get`」查变体（_move / _attack / _dormant / _awaken / _enraged / _white）。Boss 专用分支 `knight_animation`、`boss_strip_animation`、`ishar_animation` 对每只都要调用一遍（普通怪 match 落空；骑士、伊祖米克、塑路者还要遍历 `g.warns`）。
2. **算颜色 / 缩放 / 挤压 / 锚点**（约 40 行）：底色（tint、进化、无敌、晕眩）是离散的；狂暴脉动、nova、阶段护盾、自爆 / 爆发鼓胀、Boss 出招姿态、部件心跳、装填跪地、空中高度会随 g.t 连续变化。
3. **发绘制**：描边 `_spr_outline`、本体 `vfx.spr`、白闪、词条、弱点菱形，外加少数状态特效圆 / 弧。
4. **写回状态**（必须每帧照做，否则后面的帧会变）：`e.mv_until` / `e.dpos`（移动判定）、`e.atk_until`（攻击帧收尾，蓄力时 +0.2 秒）、`e.squash`（自爆鼓胀）。这三个字段只有画面读，不影响玩法。

**缓存内容**（每只敌人一个 Array `e.dc`，render 层自己写，不改模拟代码）：本体 / 描边 / 白剪影的贴图引用（省掉名字拼接和 `g.tex` 查找）、帧数、帧号、源矩形、目标尺寸与锚点偏移、翻转、高清倍率、底色、描边色与开关；再加两个失效依据 `valid_until`（时刻）和 `sig`（状态签名）。

**失效条件**（任何一条满足就整段重算，结果写回缓存）：
- **时间窗**：重算时一并算出 `valid_until` = 最早的「画面会变」时刻，包括下一次帧号跳变（按该帧条的 fps 和 `e.id` 相位）、`mv_until` / `atk_until` / `wake_t` / `prepare` / 冲刺·蓄力阶段界、白闪结束；`g.t ≥ valid_until` 就重算。
- **状态签名**：每帧只读一组离散字段拼成一个整数，和上次比较：贴图基名、phase、coma、stun > 0、evo、invuln、enraged、dormant、elite、各蓄力计时器是否 > 0、pose > 0、fx 正负、`outline_skip`、`Cfg.outline`、`ecrowd` 档位（描边透明度按 0.05 分档）。签名变了就重算。
- **不进缓存、每帧照旧整段算**（明确排除）：所有 Boss（含 `knight_animation` / `boss_strip_animation` / `ishar_animation` 专用帧条）、部件、宝箱、潜地，以及任何连续变化状态正在生效的敌人（狂暴脉动、nova、阶段护盾、blast / burst 鼓胀、出招姿态、空中、装填跪地、剑光）。这类每帧通常 ≤ 10 只。

**每帧仍照做的**：位置与击退偏移 `draw_off`、是否在白闪、上面那三个写回、冲刺火花（vrng）、词条（已进无贴图批，§9.7）、弱点菱形。

**预计收益（不确定）**：稳态普通怪每帧从「约 60 次字典读取 + 约 6 次字符串拼接查找 + 3 个 Boss 分支调用」降到「约 15 次读取 + 一次整数比较」，再加发绘制。粗估 GDScript 侧每只 19 → 8–12 微秒，160 只在安静时段省约 1–1.7 毫秒。但签名本身要读十几个字段，§9.8 的教训是「查表不是瓶颈」，所以**真实收益可能远小于估计**，必须先量。

**第 0 步：先量（半天，探针分支不合入）**：给 draw_enemy 分块计时（选帧 / 算色 / 发绘制 / 写回），再空跑一遍签名计算；用 `--fixed-fps 60`、同局按秒轮换（§9.6 的方法）。得出「可被缓存跳过的那部分」和「签名成本」各自几毫秒。可省部分（选帧 + 算色 − 签名）≥ 1 毫秒（安静时段折算）才进第 1 步。

**第 1 步：实现与对照（约 1 天）**：
- render/world.gd：draw_enemy 拆成「算参数」（纯计算，写 `e.dc`，含三个写回）和「按参数发绘制」；Boss 等排除项仍走原路径。
- **逐像素一致**：`--fixed-fps 60` 同 seed、同参数，新旧各跑到 10:00，每 30 帧抓一次画面哈希，差异必须为 0；不一致就输出第一帧差异的截图对。
- **自检开关**：`--dccheck` 时每帧对约 5% 的敌人同时走新旧两条路径、比较参数，不一致就报 SCRIPT ERROR；快检冒烟里开着，防止以后有人加状态却没加进签名，导致画面过期。
- **随机数**：draw_enemy 现在不消耗 `g.rng`（冲刺火花用 vrng、每帧照画），缓存不改变任何消耗顺序。
