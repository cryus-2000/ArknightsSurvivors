> 用户问"测试能不能优化"：本机 Godot 名额经常排队，各会话各跑一遍 check.py 和 A/B。本文先给实测数据，再逐项评估，最后给推荐顺序。

## 1. 各项评估

每项写：预计省多少、工作量、风险。

### 1.1 批跑和 A/B 整体放云端，本机只留冒烟 / 截图（主方案）

- **做法**：会话在自己的工作分支上改完 → 推分支 → 云端 `AB=<基准提交> bash tools/cloud/run_cloud.sh`（或 `PRESET=…`）→ 结果推 `cloud-results/<名>` → 本机 `git fetch` 读报告。本机只跑：快检（合入前）、截图 / 图鉴、单局调试。
- **省多少**：本机每天约 95 进程小时的批跑全部移走；本机快检回到不受挤压的 5–6 分钟；批跑本身在云端并行跑，按今天云端快检 35 秒的速度推算，一组 100 局左右的对比从本机的 1–2 小时降到十几分钟。
- **工作量**：小。脚本已经有（tools/cloud/），缺的是流程：谁触发云端、结果怎么通知。建议由我（测试与验收）统一接云端请求：各会话【任务】给我"分支 + 基准 + 预设"，我跑完回报告。
- **风险**：
  1. 云端和本机结果不能互比（已定规则）；过渡期要避免"本机基准 + 云端改动"的混用。
  2. 云端机器的结果缓存是临时的，换一台机器就没了（见 1.2）。
  3. 推分支要记得合入后删远端临时分支（docs/41 已写）。

### 1.2 A/B 基准按提交共享（按提交 + 矩阵做 key）

- **现状**：结果缓存 key 是"游戏源文件内容摘要 + 参数"，已经跨工作树共享；但 main 一天变 25 次左右，每次都是新摘要，所以只命中 7%。而且主工作区以前常有别人未提交的改动，也会让摘要变化（新规则后主工作区不留改动，这个问题会减轻）。
- **做法**：每当 main 前进，云端按固定几组矩阵（starts / opcmp / share）跑一次基准，结果推 `cloud-results/base-<提交>`；各会话做 A/B 时直接取这份基准，只跑改动侧。缓存 key 要加上**平台**（现在的 key 没有平台，将来本机和云端缓存一旦共用就会混）。
- **省多少**：今天基准侧 596 局 / 33 小时；若 A/B 大多以当时的 main 为基准，可省其中大部分（估 70–80%）。
- **工作量**：中。要做：key 加平台；云端"main 前进就跑基准"的触发；取回基准结果并导入缓存的小脚本。
- **风险**：矩阵参数一改就要重跑基准（key 里本来就有参数，不会用错）；main 合入太频繁时基准会排队，可以只给"被 A/B 引用到的提交"补跑。

### 1.3 check.py 分级：按改动文件自动选项目，合入前才全量

- **做法**：`check.py --auto` 对比 merge-base 看改了哪些文件：

  | 改动 | 跑什么 | Godot 数 |
  |---|---|---|
  | 只有 docs / *.md / art 预览图 | 不开 Godot，只做 JSON 格式和引用检查 | 0 |
  | data/*.json 只改了 desc / name 等说明字段 | 核心契约测试 | 1 |
  | 单个干员的 .gd / .json | 核心 + 该干员冒烟 + 该干员成长节点 + 复现 | 5 |
  | 共享代码（game.gd、run/、core/、combat、relic_fx 等） | 全量 | 31 |

  快进合入 main 前仍必须跑全量（本机或云端）。
- **省多少**：改文档、改说明、改单个干员的提交占多数，这些从 31 个 Godot 降到 0–5 个，单次快检从 5–10 分钟降到 1–2 分钟。
- **工作量**：小到中（改动分类规则 + 一张映射表）。
- **风险**：漏掉跨干员的影响（例如改了某干员的藏品联动）。靠"合入前全量"兜底，所以风险可控。

### 1.4 godot_runner 全机统一排队 + 优先级

- **现状**：每次启动前加锁数 Godot 进程，没满就起；没有先来后到，也没有优先级，大批跑会把合入前的快检和截图挤到后面。每会话 ≤4 的约定以前做不到（线程池和全机上限共用一个数），f0a2053 给 check.py 加了 `--jobs`，balance_run 本来就有 `--jobs`。
- **做法**：在 `build/.godot_queue/` 放排队票据（进程号 + 优先级 + 时间），高优先级（合入前快检、截图）先走，低优先级（批跑）只在没有高优先级在等时才起；进程死了的票据按进程号清理。
- **省多少**：批跑移到云端后本机争用会少很多，这项的价值随之变小；主要收益是"合入前快检不再被挤到 10 分钟"。
- **工作量**：中。**风险**：票据残留导致卡死（要按进程号存活判断清理）；实现不当会饿死低优先级。
- **建议**：先做 1.1，观察一周本机是否还排队，再决定做不做。

### 1.5 大批跑搬云端的时机

- 已具备：环境脚本、快检 35 秒通过、跨平台规则定稿、分支可推。
- 还缺：谁来触发、结果怎么回来（1.1 的流程）和基准共享（1.2）。
- **建议**：现在就切。第一周由我代各会话跑云端（它们发【任务】），同时把 1.2 的"main 基准"跑起来；过渡期内同一个 A/B 两边都在云端算。

### 1.6 负载高时快检偶发一项失败

- **已做**（f0a2053）：失败时列出失败项、原因、日志路径；每局完整输出落盘；记下开始 / 结束时全机 Godot 数。下次再出现就能看到是哪项、什么原因。
- **已知一次**：全机约 40 个 Godot 时，「同 seed 复现」失败，两局的 boss_hp / bosses / dmg 等字段不同；限 4 路单独重跑通过。
- **已排除**：
  - 模拟步长：平衡模式固定 0.066 秒一步，不受负载影响；玩法只在 game.gd 的主循环里推进，没有别的节点用真实帧间隔改玩法状态。
  - 语音：按真实时钟决定"是否正在播"，但不消耗带种子的随机数；战斗台词计时用模拟时间和 g.rng。
  - 合成按键的 0.35 秒保护：只作用于手柄转键盘，机器人不走这条路。
- **还要查**：超时（run_case 300 秒，满载时一局 240 秒游戏时长可能跑不完，这会报"有一局没跑完"而不是字段不同）；把复现两局放在人为加压（同时起一批空跑的 Godot）下反复跑，看分叉点。另有「Fix Saria-start nondeterminism under load」会话在查同类问题，结论出来后合并。

4. **1.6 负载敏感排查**（日志已就位，等下一次出现或主动加压复现）。
5. **1.7 出手帧截图开关**（美术验收常用）。
6. **1.4 统一排队 + 优先级**（上云后观察一周再定）。
